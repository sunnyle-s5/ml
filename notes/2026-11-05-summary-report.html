Game recommendation: v1 → v3 summary and live-POC proposal

sunny · ML VM (S5VM-24) · 5 Nov 2026 · all numbers offline, from frozen weekly backtests (20 scored clusters, 8 markets), read-only. Nothing has been sent or deployed.

In one paragraph. Our current list (v1) already beats the site's Popular list by 15–41 pt HR@10 offline. Most of that comes from showing players their own recent games, not from the model. The ideas worth taking from the v2 and v3 reference designs are:
  • learn which own games to show, together with new games, in one ranker: +1.13 pt HR@10 on 20/20 clusters (v3);
  • give returning players without a list their own older games: +12.7 to +17.8 pt on their first day back (v3).
The LLM parts of v3 and most of v2 do not help HR@10 with our data. Proposed for the live POC: the v3 "unified" personal list on ADDA7 with the cold-player fallback, against the live Popular list and a no-ML "own games + Popular" arm. Release gate: the 11 Nov re-test and the dims-pull fix.

Metric. HR@10 = the share of scored players (they had a personal list and played in the following week) who played at least one of the list's first 10 games that week. New-game HR = the same, counting only games the player hadn't played in the 60 days before. Reference week: 27 Oct–2 Nov 2026 (as of 26 Oct), 1,383,665 scored players.

2 · v2 ("Personalized Category & Provider Grids"): what works / won't

The v2 spec was written for another stack (BigQuery, wallet CDC, Redis). It was read as a source of ideas, and where it conflicts with our data, our data wins. Five experiments were run on 20 clusters × 2 weeks, plus the POC brand ADDA7.

4 · Proposed final model for the live POC

Release candidate: "personal list v3"
  • Players with a personal list: the v3 unified ranker, top 10. A LightGBM model scores the player's 20 most recent own games together with new-game candidates (ranker new 10, popular 10, live top 20), trained daily on the previous week.
    • Discovery-preserving alternative if Product prefers: learned continue (3/5), at +0.77 pt with unchanged new-game HR.
  • Returning players without a list (no play in 30 days, but earlier play): their 5 most recent earlier games, then the live Popular list.
  • Newcomers: the live Popular list (unchanged).
  • Fallback (no file row, stale file, error): the live Popular list, with fallbackReason logged.

POC design

ItemProposal
Brand / surfaceADDA7 (bdk1, Bangladesh): 64,040 scored players a week. Detectable difference (α 0.05, 80 % power): 1.1 pt at 50/50, ≈ 1.35 pt per pair with the four arms below. Surface: home main_list.
Arms (person-level, sticky)17 % control A1 (live Popular) · 17 % control A2 (live Popular; the A/A check) · 33 % H = own games + live Popular, no ML · 33 % B = personal list v3
Expected offline on ADDA7Live 78.9 % · H 92.9 % · v1 default 93.8 % · v3 unified 94.5 % (27 Oct–2 Nov)
Primary metricShare of exposed players who open ≥ 1 game from main_list positions 1–10 within 7 days (the online twin of HR@10)
SecondaryGame opens per player across all surfaces (incrementality vs last_played); new-game opens; adoption (a new game played on ≥ 2 days); stratum "had a personal list at exposure"
Duration / decision14 days. B vs A1+A2 is the main test, and B vs H shows whether the ML adds anything over pinning. Ship if B wins with PostHog chance-to-win ≥ 95 % and no guardrail breaks.
DeliveryDaily per-player S3 file (recs/<list_date>_<cluster>.parquet: account_id, member, rk, game_id, slot, list_id) read by the BE. Two FE event changes, one PostHog flag. Spec: drafts/spec-game-list-impression-and-ab.md.

Why this one

  • It is the best list measured on our data: +1.13 pt over v1 on every cluster, built only from features the pipeline already has, with no new data sources and no LLM.
  • Running cost is small: one extra LightGBM per cluster per day. The full 20-cluster run took 9 minutes on the VM (peak 9.3 GB), similar in size to the existing step-14 ranker.
  • Arm H protects the decision. Offline, pinning own games carries ~90 % of the gain, so if H ≈ B online, the cheapest product is a site-side change and the model is not needed.
Conditions before release
  1. Second forward week (Wed 11 Nov): re-run experiments/2026-11-05-v3-unified/run.py all.
    • The unified list must again beat the default by ≥ 0.5 pt pooled on ≥ 15/20 clusters.
    • If it fails, release v1 default (hybrid recent continue + ranker new) as arm B instead; everything else stays the same.
    • That week is the first built with EASE on, so check meta.ranker_ease_cands when reading it.
  2. Dims pull fixed: pull_dims.py still selects the dropped column freeSpinEnabled (179 errors today). Until it's fixed, no new games enter any list.
  3. Productionise in the pipeline: a patch to build_recs.py (unified ranker + returning-cold list) and a new export_recs.py, applied by Yann. The live pipeline cannot be changed from this account.
  4. Tech-team work: BE serving, FE list identity in events, the PostHog flag, and S3 read access (Harvey). The RG review is in a separate session.

Trade-off to note

The extra HR@10 is mostly replays of the player's own games: new-game HR falls from 19.4 % to 14.0 %, and the site's last-played row already shows some of those games. If discovery matters to Product, use the learned-continue variant (+0.77 pt, new-game HR unchanged). The live A/B's "opens per player across all surfaces" metric shows whether the list adds play or only moves clicks.
